# 06 · 工具召回、上下文与缓存

上一篇：[05 执行与安全](./05-execution-security.md) · 下一篇：[07 桌面与 MCP](./07-ui-and-mcp.md)

## 本篇目标

工具数量增长后，瓶颈会从“能不能调用”变成“模型能否在有限上下文里稳定看到正确的工具”。本篇解释召回、排序、缓存、历史和结果预算如何共同工作。

重点源码：[`src/core/retrieve.ts`](../src/core/retrieve.ts)、[`src/index.ts`](../src/index.ts)、[`src/agent/prompts.ts`](../src/agent/prompts.ts)、[`src/agent/loop.ts`](../src/agent/loop.ts)。

## 1. 工具 schema 也是上下文

假设仓库有 500 件工具，每件名称、描述和参数平均几百字。如果每一步全量注入：

- 有效任务信息被稀释；
- 输入 token 与延迟增加；
- 模型更容易选错相似工具；
- 工具数组轻微变化就可能破坏前缀缓存。

ToolForge 的策略不是先做复杂向量数据库，而是：**轻量检索 + 固定核心工具 + 稳定序列化 + 本轮缓存。**

## 2. 两级工具发现

系统中“找工具”有两个互补入口：

1. **模型显式检索**：`list_tools` 查看全量概要，`tool_search` 根据任务查询并返回轻量索引；
2. **请求前自动召回**：`ToolForge.chat()` 用 `selectTools()` 选出本轮要注入的完整 schemas。

`tool_search` 返回的 `indexOf()` 只含名称、描述、信任和标签，适合省 token 地浏览；真正 function calling 仍需要 `toOpenAITool()` 输出的完整 `parameters`。

## 3. `selectTools()` 的评分方式

当前召回是确定性的本地词元评分，不是向量模型：

```text
名称命中   +3
标签命中   +2
描述命中   +1
上次运行成功 +0.5（对整件工具提权）
```

分词规则：

- 英文和数字按分隔符切词；
- 中文文本生成相邻二字词，短中文词也保留；
- 忽略大小写；
- 工具名中的下划线先转为空格再参与名称评分。

`always` 中的工具固定保留，目前包括：

```text
tool_search / list_tools / create_tool
```

`chat()` 自动召回使用 `limit:14`，再附加固定元工具。`manage_tool` 虽然也是元工具，但不在固定名单中，需要靠相关查询召回。

这意味着工具描述质量会直接影响发现率。一个名字无法涵盖所有同义词时，应把用途写进描述与标签，而不是把几十个关键词塞进工具名。

### 零分工具也可能被选中

评分后所有工具都参与排序，代码并没有 `score > 0` 的过滤。因此查询完全不匹配时，仍会按排序结果补足名额。这不是严格语义搜索，更不是“只返回相关项”的保证；设计新召回算法时应明确零分策略和评估集。

## 4. 为什么最终按名字排序

召回评分里有 `lastRun.ok` 提权。一次工具成功后，`lastRun` 改变，若直接按分数输出，工具数组顺序也会变化。

对于前缀缓存，**相同元素换一种顺序也是不同字节序列**。因此当前实现分两步：

1. 分数决定“选哪些”；
2. 名称字典序决定“怎样排”。

这样即使运行健康状态改变，已选集合不变时，`tools` 的序列化顺序仍稳定。排序不只是审美，是缓存设计的一部分。

## 5. `chat()` 的本轮工具冻结与指纹失效

`toolProvider()` 不是每个 step 都无条件重新评分。它维护：

```ts
frozen = {
  sig: 'name@version\nname@version\n...',
  bundles: selectedToolSchemas,
};
```

逻辑是：

```text
计算当前全部可用工具的 name@version 排序指纹
  │
  ├─ 与 frozen.sig 相同 → 复用 bundles
  └─ 不同               → 根据用户消息重新 selectTools，更新 frozen
```

### 为什么需要缓存

`store.recordRun()` 会在每次普通工具执行后写 `lastRun`。如果每步重算，刚执行成功的工具得分变化，下一步的 schema 集合与顺序可能变化，导致模型请求前缀反复 miss。

### 为什么不能整轮永不刷新

`create_tool` 创建新工具后，名称列表变化；同名重建还会版本变化。如果始终冻结，模型就看不到刚创建的能力，或者继续拿旧 schema。

`name@version` 指纹是在这两个目标之间的折中：**清单没变就稳定，创建或重建就失效。**

注意，它只跟踪名称和版本。状态、描述或 schema 被其他路径原地修改而版本不变时，指纹未必感知，这也是新增修改入口要遵守版本与缓存约束的原因。

## 6. 召回查询来自哪里

自动召回的 query 是当前 `messages` 中所有 `role:'user'` 内容的拼接，而不是每一步新产生的工具结果或 reasoning。工具结果不会直接改变召回关键词。

优点：

- 用户意图是相对稳定的前缀依据；
- 工具输出再大，也不会任意改变工具评分输入。

限制：

- 多轮话题变化后，旧用户消息仍占评分权重；
- 隐含在工具结果里的后续需求不会触发新的关键词；
- 没有真正的语义向量召回，近义词依赖描述覆盖。

`tool_search` 则允许模型用一个新的、更聚焦的查询主动补充发现，但新发现的工具是否进入当前 `toolProvider` 的 schema 集合，还受本轮指纹与重新召回规则影响；检索结果本身不会直接修改冻结集合。

## 7. 历史裁剪要保住缓存前缀

`trimHistory()` 的策略：

1. 只保留字符串内容的 user / assistant 消息；
2. 从最新向最旧累计，预算为 20000 字；
3. 超预算才截断；
4. 将起点向前调整到最近一条 user，避免只留半个问答。

不建议用固定 `slice(-8)` 每轮移动窗口。固定窗口即使内容仍不大，也会让起点每轮变化，缓存前缀整体失效。

这里预算单位是 **JavaScript 字符串字符数**，不是模型 tokenizer 的 token 数。它是工程近似，不保证恰好适配任意模型的上下文窗口。

### 两层历史限制

- 渲染层本地任务历史用更大的字符预算控制 `localStorage`；
- 后端发送模型前再用 `trimHistory()` 控制本轮输入。

CLI 也有自己的历史保存策略。理解缓存时要看真正发给 `runLoop()` 的 messages，而不是只看 UI 保存了多少条。

## 8. 系统提示词与工具库存

`buildSystemMessages()` 根据模式选择：

- `workPrompt(tools, workspace)`：执行任务、先复用后创建、带当前工作区和工具名称/信任概览；
- `createPrompt`：专注工具设计、声明式优先、权限和用例规则。

提示词中的 `inventory()` 最多列前 40 件工具，并附总数；它不是完整 schema 注入。完整 schema 由 `toolProvider()` 单独提供。

工作区路径进入系统提示词，所以同一份历史在不同工作区运行时，系统前缀本来就应该不同。不要为了追求缓存复用而把不同安全上下文混为一谈。

## 9. 模型上下文中的几种“长度”

| 位置 | 当前限制/策略 | 作用 |
| --- | --- | --- |
| 工具召回 | 默认 14 + pinned 元工具 | 控制 schema 数量 |
| 工具库存提示词 | 最多展示 40 件概要 | 控制系统提示词长度 |
| 发送历史 | 20000 字近似预算 | 控制历史输入 |
| 工具结果回灌 | 12000 字截断 | 防单次结果撑爆上下文 |
| 单轮步数 | 默认 120，封顶 500 | 防无限循环，不等同 token 限额 |

这些数字是互相独立的保险丝。历史没超不代表本轮总 token 没超，因为系统提示词、工具 schemas、每步 assistant/tool 消息也会累积。

## 10. token 用量和缓存命中不是估算

`streamOnce()` 从流里的 `usage` 读取真实回报，兼容：

- `prompt_cache_hit_tokens`；
- `prompt_tokens_details.cached_tokens`；
- 对应的 prompt、miss、completion 字段。

`chat()` 将各步用量累加后返回。CLI 可据此打印命中率。

如果服务商不回报 usage，就只能显示未知，不能用字符预算反推出一个看似精确的命中率。评估优化时还要记录模型、服务商与请求形状，因为不同实现的缓存规则可能不同。

## 11. 如何评估一套召回算法

不要只凭“这次找到了”判断好坏。至少准备：

```text
query → 应该入选的工具集合 → 不应该入选的相似工具
```

覆盖：

- 中文、英文、大小写、下划线；
- 同义描述与零相关查询；
- 工具数超过召回上限；
- pinned 工具永远存在；
- lastRun 变化不改变已选集合的序列化顺序；
- 创建与同名重建能触发指纹失效；
- 缓存命中与正确性的平衡。

若未来引入向量检索，建议保留确定性 tie-break 和最终稳定排序，并为索引版本、嵌入模型版本及重建策略留下元数据，否则“同一工具库”其实会随索引实现变化。

## 动手练习

1. 构造 20 件名字相近的工具，观察 `selectTools()` 在中文、英文和无匹配 query 下的输出。
2. 修改一件工具的 `lastRun.ok`，验证入选集合不变时名称排序不变；再故意按分数排序，比较 JSON 字符串。
3. 创建一个工具，观察 `name@version` 指纹何时变化；同名修复后再观察一次。
4. 用短历史重复运行同一任务，记录服务商回报的真实缓存命中，不要只按消息长度推断。
5. 设计一个召回回归测试：必须能找到目标工具，同时必须排除一个名字相似但权限完全不同的工具。
