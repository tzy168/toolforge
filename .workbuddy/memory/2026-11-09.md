# 2026-11-09

## 权限体系：命令分级 + human-in-loop + 三级访问档位

- 新增 `src/core/policy.ts`：`AccessLevel = full/workspace/readonly`；`effectivePermissions()` 只收窄不放宽、不改落盘规格；`classifyCommand()` 把命令分 deny / confirm / allow 三档，清单外默认拒绝，硬红线不接受人工放行；workspace 档校验 `impl.cwd` 必须落在工作区。
- 新增 `src/core/approval.ts`：挂起 `executeTool` → 发 `approval_request` 事件 → 等 `tf:decideApproval`；超时与暂停按拒绝收尾；`allow_always` 只记内存、会话级。**人的决定必须由 `executeTool` 返回值经 `loop.ts` 的 `role=tool` 消息回灌模型**——只改状态不回话，模型会反复重试同一条命令。
- 档位按轮由 `chat({ access })` 传入（与 workspace 同理，不做全局开关）；`ToolForge.runTool` 补挡不经 executeTool 的元工具（create_tool / manage_tool 破坏性动作）。CLI 构造时注入 `approvalResponder` 自动拒绝并打印，桌面端走 UI 确认条。
- UI：输入框右侧档位胶囊（三项）+ 聊天区上方确认条；新增 `tf:decideApproval` / `tf:setAccess` 两条 IPC。
- 顺手修 `runShell` 的 env：`execFile` 传 env 会替换整个环境，原先只给声明过的键，Windows 上连 PATH 都没有，放行的命令也找不到可执行文件；现补 PATH / SYSTEMROOT，与 `script.ts` 的 `childEnv` 一致。
- 验证：typecheck / build 通过；单测 35/35；selftest 13/13（临时 TOOLFORGE_HOME）；verify:switch 25/25；verify:toolfilter 25/25；Electron smoke 验证档位点击与桥接。两处变异验证（放行禁止清单、抹掉回灌文案）均确认断言会红。
- 坑：直接跑 `pnpm selftest` 会用到真实 `~/.toolforge`，旧仓库缺种子工具会报 3 项红；必须带 `TOOLFORGE_HOME` 指临时目录。

## 第二轮：把权限从「执行时拒绝」前置到「选工具之前」

- 用户实测反馈：readonly 档下模型仍连试 12 件工具、8 件失败，才告诉用户要切档位。根因是工具集全量注入 + `create_tool` 被 `always` 强制置顶 + 权限说明挂在提示词末尾 + 「缺能力就造工具 / 失败再来一次」两条原则反在鼓励试探。
- `policy.ts` 加 `toolAvailable / filterTools / hiddenToolNames`；`accessDenies` 复用同一判定，文案强调「换任何工具重试都不会成功」。
- `chat()` 的 `toolProvider`、`buildSystemMessages`、`MetaContext.allTools()` 三处都过滤；`selectTools` 的 always 按可见集合裁剪；`list_tools` 标 `blockedByAccess`，`tool_search` 只搜可见工具；`loop.ts` 的「没有名为 X 的工具」补「可能已被档位隐藏」。
- `accessNote` 移到系统消息最前，点名隐藏工具，明写「不要调用任何工具去试探」；`workPrompt` 第 1 条改为权限先行。
- 验证：typecheck/build、单测 39/39、selftest 13/13、verify:switch 25/25、verify:toolfilter 25/25；变异（去掉 toolProvider 的 filterTools）确认断言会红。
